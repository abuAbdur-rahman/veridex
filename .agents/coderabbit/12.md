### 4. Handle transport failures after `reply.hijack()`

- Severity: Major
- Category: Stability and availability
- Location: `apps/server/src/routes/mcp.ts:215-231`
- Finding: After `reply.hijack()`, Fastify cannot write a response. If `transport.handleRequest` rejects, the client connection stays open until a socket timeout, and `server.close()` is never reached because the await throws first — leaking the MCP server and transport per failed request.
- Recommendation: Wrap the transport call in try/catch/finally; log the error, write a JSON-RPC internal-error response when headers are unsent, destroy the raw socket otherwise, and close the server in finally.
- Source: https://github.com/abuAbdur-rahman/veridex/pull/12#discussion_r_pull12-inline-4

### 5. Status transitions lack compare-and-set under concurrency

- Severity: Major
- Category: Data integrity and integration
- Location: `apps/server/src/test/issue-service.integration.test.ts:144-169` (`apps/server/src/services/issue.service.ts` updateStatus)
- Finding: `updateStatus` reads `fromStatus` before its transaction, but its update predicate matches only `issueId` and `projectId`. Concurrent callers can all read `"in_progress"` and each write `"backlog"` plus insert history — multiple winners and duplicate transition records.
- Recommendation: Include the expected current status in the issues update predicate alongside issueId/projectId and throw a conflict when the conditional update returns no row.
- Source: https://github.com/abuAbdur-rahman/veridex/pull/12#discussion_r_pull12-inline-5

### 6. NOTIFY payload guard is off by one byte

- Severity: Minor
- Category: Stability and availability
- Location: `apps/server/src/ws/broadcaster.ts:103`
- Finding: PostgreSQL requires `NOTIFY` payloads strictly shorter than 8,000 bytes. The guard uses `> MAX_PAYLOAD_BYTES`, accepting exactly 8,000 bytes which PostgreSQL then rejects.
- Recommendation: Reject with `>= MAX_PAYLOAD_BYTES` and add a boundary test covering exactly MAX_PAYLOAD_BYTES.
- Source: https://github.com/abuAbdur-rahman/veridex/pull/12#discussion_r_pull12-inline-6

### 7. `isWsEvent` accepts unknown event types

- Severity: Minor
- Category: Data integrity and integration
- Location: `apps/server/src/ws/broadcaster.ts:127-138`
- Finding: The validator only checks that `type` is a string and `payload.projectId` a string, so `{ type: "unexpected", payload: { projectId } }` passes and `handleRemoteBroadcast` forwards it to project clients.
- Recommendation: Validate the full WsEvent schema — restrict type to supported discriminants and validate each required payload field; reject unknown types before local delivery; add coverage for an unknown type with a valid projectId.
- Source: https://github.com/abuAbdur-rahman/veridex/pull/12#discussion_r_pull12-inline-7
